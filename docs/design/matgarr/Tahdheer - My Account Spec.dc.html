Audit finding that changes the plan

The brief's §11–§13 assume an existing multilingual system to integrate with. There is none. inc/setup.php:16 calls load_theme_textdomain('tahdheer', …/languages), but no WPML, Polylang or TranslatePress is present and there is no language switcher anywhere in the theme. Arabic today comes from two filters — woocommerce_account_menu_items (inc/woocommerce.php:63) and a page-title filter — not from a translation layer. There are also no myaccount/ template overrides: the account page is stock WooCommerce output, which is why the default «Hello username / From your account dashboard» paragraph is still printed. Decision required before build: install Polylang/WPML, or build an in-theme locale layer on .po files. This spec assumes the second, being lighter and dependency-free, and marks the parts that change if you pick the first.

1 · Endpoints

Native endpoints keep working untouched (brief §172). Four are added; each is registered once and flushed on activation only — never on every load.

EndpointSlugNotes
LibrarylibraryThe centrepiece. Derived from download permissions + order items, not a new store.
PreferencespreferencesStage / grade / subject / semester on user meta; reuses existing taxonomies.
SecuritysecurityOnly real states: password-changed date, active sessions via WP_Session_Tokens. No fake 2FA (§113).
SupportsupportWhatsApp deep link from the existing whatsapp_number option + FAQ links.

Slugs stay Latin in both languages. Localise the visible label, never the URL — per-language slugs double the rewrite table and break bookmarks on switch. Language switching must preserve the endpoint and the session (§12–§13, §176): swap only the locale query var/cookie and re-render the same endpoint.

2 · Data service

One class, one request, memoised. Templates consume prepared arrays and never query (§182).

inc/account/class-account-data.php

  ::for_user( $user_id )        one instance per request, memoised
  ->stats()                    orders, library, downloads, wishlist
  ->orders( $limit )           wc_get_orders, customer-scoped
  ->owned_product_ids()        one query, reused by library + recommendations
  ->library( $filters )        owned + downloadable, with edu meta
  ->downloads()                wc_get_customer_available_downloads
  ->updates()                  post_modified > order date, owned only
  ->progress( $subject )       owned ÷ catalogue relationship
  ->recommendations()          deterministic; excludes owned
  ->features()                 capability map — see §3

N+1 avoidance: owned_product_ids() runs once and every downstream method takes it as input — library, updates, progress and recommendations must not each re-derive ownership. Cache: per-user transient keyed tah_acct_{user_id}_{hash}, private only, invalidated on woocommerce_order_status_changed, woocommerce_grant_product_download_permissions, profile update and wishlist change (§190–§192). Never a public/page cache on these endpoints, and nocache_headers() on all of them.

3 · Feature detection — what is real today

§145 forbids UI for absent features. The audit found none of the following in the theme, so the dashboard lists them as «يحتاج ربطًا» rather than drawing them with invented numbers.

ModuleStatusDetection gate
Orders · Downloads · LibraryReal nowWooCommerce core + _tahdheer_* edu meta.
Purchase updatesReal nowDerived from post_modified vs. purchase date. Show a re-download link only if a new file actually exists.
WishlistPlugin-dependentGate on the plugin's own function existing. Hide the module otherwise.
Wallet · Rewards · CouponsAbsentNo balance, ledger or points store exists. Each needs a real backend before any panel ships.
PDF invoicesAbsentOrder view exists; PDF generation does not. Do not print a Download-PDF button that 404s.
Notification centreAbsentNeeds an events table. Store structured events and translate at display (§64) — never store pre-translated text.
Two-factor authAbsent§113: never render a 2FA toggle that does nothing — it is a safety claim, not a decoration.
